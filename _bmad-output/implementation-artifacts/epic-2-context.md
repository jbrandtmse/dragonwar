## Goal

Epic 2 turns Epic 1's placeholder vertical slice into a machine a stranger can play with no instructions. The real playfield geometry is drawn for the first time — the drain triangle, both Loops, the Ramp, the off-centre Dragon with the Lock lane between its legs, the DRAGON drop bank, Top lanes, slings and pops — and every device on it is wired into the table registry with a switch that registers reliably at the fastest speed the physics core can produce. On that geometry sits the whole standard game: Start and Hot seat for one to four players, the ball lifecycle, plunge and Skill shot, lane change, ball save, end-of-ball bonus and multiplier, tilt warnings, Tilt and Slam tilt, ball search, Match, game over and a return to a minimal Attract — all readable from a DMD Backglass with the inserts lit in the table's fixed colour grammar. Geometry is the first story and iterates with the rules that land on it.

## Technical Decisions

- **AD-19's devices-and-shots layer is DELIVERED and is the substrate every remaining rules story consumes.** `src/sim/rules/devices/` is the **only** consumer of `SwitchEvent`; `src/sim/rules/index.ts` no longer names it, reaching the input type through `Parameters<DevicesLayer['step']>` instead. `createRules()` is instantiated per loop, mirroring `createMachine()`. The layer owns the drop bank (letters and the reset coil, which it **alone** pulses — on `ball_will_start` and on `bank_completed`), the spinner count, ball-device slots, the shooter lane, and the declared shots. It emits only payload-complete device events: `shot_<name>_made` / `_broken`, `bank_target_down { letter }`, `bank_completed`, `dragon_hit`, `lock_lane_entered`, `spinner_spin { count }`, `lane_entered { lane }`, `lane_change_pressed { side }`, `ball_launched`, `device_ball_entered { device, slot }`, `device_ball_left { device, slot }`, `button_pressed { button }`. **Modes, scoring and the ball controller consume device and shot events and never a raw switch.** Lane *state* (lit flags, completed sets) belongs to the base mode; this layer reports lane entries and lane-change presses only. **Two documented, by-design gaps to know before filing them as defects:** `ramp_made` is named in AD-19's Rule and in the epic's prose but is **never emitted** — a made Ramp surfaces as `shot_ramp_made`; and **the two Loops can never emit `shot_<name>_broken`**, a direct consequence of `entryExclusive: false` below.
- **The rules→physics coil channel now exists — Story 2.5's ball controller needs it.** `RulesStepResult.coilCommands` is queued into `pendingCommands` and consumed on the next tick (AD-4); before 2.4 there was no such channel at all. `FrameOutput.commands` deliberately stays presentation-only (`RulesStepResult.commands` is typed `readonly never[]`). This is the channel through which the ball controller pulses `c_trough_eject`, `c_autolaunch` and `c_mouth`.
- **Shots are declared data, not code.** `TABLE.shots` is declared (no longer `{}`): `shot_left_loop = [s_loop_l_in, s_loop_l_out]` and `shot_right_loop` within `loopWindowMs` (600), `shot_ramp = [s_ramp_enter, s_ramp_made]` within `rampWindowMs`. In order inside the window emits made; a broken sequence or an expired window emits broken; a Loop taken the wrong way emits nothing. `ShotName` is `keyof typeof TABLE.shots`, so the union members now exist. **`entryExclusive` records a MEASURED geometric fact, never a style choice** (`DW-133`): `false` when something other than the shot also closes its own first switch, `true` when nothing does. **Both Loops are `false`** — each `_in` zone spans its whole lane mouth, which also spans that side's outlane column, so **every outlane drain closes `s_loop_l_in` / `s_loop_r_in`, and so does a made Ramp** (measured `firstMakes` on a made Ramp: `s_ramp_enter, s_ramp_made, s_loop_r_in, s_inlane_r`). A sequence with `entryExclusive: false` is tracked to completion but never emits `_broken` on expiry, because emitting it would fire on both the outlane drain and the made Ramp — which *is* treating the bare `_in` as a Loop entry. **The Ramp is `true`**, so a lapsed Ramp window is a real, falsifiable rejection. **Never treat a bare `s_loop_*_in` as a Loop entry.**
- **`DW-173` is an OPEN QUESTION for the author, not work anyone should start.** Two consecutive same-side Loop orbits emit a spurious `shot_<other>_loop_made`: every made Loop ends by closing the opposite Loop's entry switch, arming it, and the next orbit's opposite `_out` completes that stale flight. The boundary is exactly `loopWindowTicks` (600) — measured spurious at 240 and 440 ticks of inter-orbit gap, clean at 640+. It is not reachable in play today (it needs a re-shot faster than a ball can return to the flipper), but **the inter-orbit margin was never measured** — `loopWindowMs`'s own source prose measures only the intra-orbit `_in`→`_out` gap (223–452 ticks). Fix-risk is HIGH: distinguishing a stale arm from a real entry needs cross-shot state, which changes `DW-133`'s resolution that all of Epic 3 consumes. Affects FR-36 (Joust's Loop alternation). **Escalated for the author's decision sheet; do not patch it blind.**
- **`lock_lane_entered` no longer over-reports, and the residual is Story 3.2's to decide.** `DW-166` is closed: the event fires only on a **resolved** lane closure, and the 550–600 mm/s band now produces silence (verified non-vacuous by deleting the gate, which reddens four tests including the real-physics 575 mm/s case, while the same test still asserts `s_lock_lane` *does* close, so it discriminates rather than asserting nothing). **`DW-166`'s own long-standing wording — "never reaches a slot" — was measured false.** The real discriminator is capture **latency**: at 575 mm/s `s_lock_lane` closes at tick 415 and `s_lock_1` at 696 (281 ticks, after rattling back down the corridor); at 800 mm/s it is 378 and 512 (134 ticks). `lockCaptureWindowMs` (180) sits inside that gap. **The surviving consequence is `DW-171`, routed to Story 3.2, NOT to 2.5:** a shot slow enough to miss the window **still parks in `bd_lock`** — `s_drain` never closes, the ball is physically held, `device_ball_entered` fires and `lock_lane_entered` does not. AD-18 makes the arbiter the sole consumer of that event and the only pulser of `c_mouth`, so only Story 3.2 can set the policy (eject the uncredited ball, credit it late, or treat `bd_lock` occupancy rather than the event as the truth). **A geometry change is the wrong answer** — it would undo the wedge fix 2.1c's bevel reversal exists for.
- **Hardware rules run inside the physics step.** Slingshots and pop bumpers join the flippers and plunger: switch closes at tick *t*, coil energises inside tick *t*'s own physics step with no rules round trip, gated only by coil enable/disable. Disabled, they act as passive rubber and emit no actuation. Every actuation emits a contact event to presentation so each mechanical sound has exactly one source; rules never receive a contact event. **They sit at different points in the tick — copy that shape rather than re-deriving it.** The slingshot *is* the ported model, registered per coil through a thin subclass that never edits the frozen port (`DW-79` — construct, subclass, inject), so its parabolic kick fires **inside the collision solve**. The pop bumper is an authored skirt device needing a switch *edge*, which exists only after the switch tracker steps, so it fires **after** that call, as an impulse directed radially away from the bumper's own footprint centroid. Three consequences worth inheriting: kick **magnitude alone cannot break a reflection symmetry** — a ball descending exactly onto an apex vertex needs a fixed, deterministic lateral floor, never randomness; reporting that a coil *branch ran* is not reporting that an impulse was *delivered*; and two `sw_pop_*` skirt zones overlap in committed geometry, so one ball can make two pop switches on a tick and fire two near-cancelling coils — escalated rather than patched, because the root fix is `sw_` geometry and another five-golden re-record.
- **`popKickMmPerS` ships at 200 and is protected rather than safe.** There is **no floor near 180** — virtually any positive kick clears the stranding case, down to 0.5 mm/s — and the landscape is **chaotic in both directions**, with the nearest re-strand at **198 mm/s, two mm/s *below* the shipped value**, and a further cliff at 221. Measured neighbours: 198 → re-strand, 199 → 126.79, 200 → 126.84, 202 → 309.72. No nearby value is better. Sentinels sit on the clearing pocket's ends so a future physics change that lands on a re-strand reddens loudly; deliberately **not** a pin on 198's re-strand, which would go red if a future change *widened* the margin.
- **Physics owns ball bodies and mechanical state; rules own accounting.** The Lock is a parking device (capacity 3, filling the lowest empty slot, ejecting the highest filled slot at the Mouth pose, one ball per pulse). **A ball device's boot occupancy is a declared property of that device, never a global constant** — a registry contract every future ball device inherits, with the lifecycle, ball-save and ball-search stories named consumers. The shooter lane is non-parking with the served ball resting simulated on the plunger tip, and **the *opening* of `s_shooter_lane` is the one event that means "plunged"** — the devices layer emits it as `ball_launched`, on which the ball controller increments `ballsInPlay`, starts the ball-save timer and arms the skill shot (which closes on the next playfield closure that is not a Top lane). Device counts are the number of closed slot switches and nothing else. A dropped target is non-collidable until the bank reset coil raises it. **The spinner is a pass-through gate, not a collision body** — thirteen-plus rigid-body variants were measured across both candidate ball paths and every one that genuinely contacted the ball produced a permanent stall, because a static rigid body cannot graze a 13.495 mm-radius ball with the precision those paths allow; the analytic swept-segment zone test is the physically correct model here, not a workaround. A node nothing collides with is not `col_`, so the spinner's node is `vis_spinner_l` and is a presentation mesh.
- **`GameState` is one plain-data tree with fixed ownership scopes** — JSON-serializable, no class instances or closures, mutated only inside the rules step. **Player-scoped** (only under `players[i]`): score, DRAGON letters, Lock credits, modes played, tilt warnings, bonus by category and multiplier, extra balls, lanes (owned by the base mode; the skill-shot mode writes the lit Top lane once on `ball_starting` from the PRNG and never again), Jackpot seed and Wars started. **Machine-scoped** (only under `machine`): device slot states and `ballsInPlay`, `hardwareEnabled`, `ballSave`, `tilt`, `multiball`, read-only high scores. **Mode-local**: the mode's own timers and counters, published to presentation only as its typed view. The mode stack is empty between balls: every active mode receives its will-stop before ball-ended; ball-will-start resets ball save, tilt and multiball; ball-starting enables hardware.
- **Single arbiters for the overloaded seams.** The **Lock arbiter** in the ball controller is the only consumer of `lock_lane_entered` and emits exactly one of locked, mode-start with candidates, strike, or spit (device full of another player's balls; the credit still counts). It alone pulses `c_mouth` and serves from the trough after a lock entry; when lock and mode start both apply it credits the lock first; the mode-select window is its timer, the ball stays parked meanwhile, flipper edges move the selection and Start or either flipper confirms; every Mouth eject is preceded by a mouth-open show and follows it by a converted lead time. **Ball save** is one machine device the ball controller owns, armed and disarmed by source through a rules-internal interface, sources stacking with the longest live window winning, Tilt disarming all; only the ball controller pulses the trough-eject and autolaunch coils and mutates `ballsInPlay`. **"A multiball is running"** is a flag set in a mode's starting phase and cleared in its stopped phase, never derived from balls in play.
- **The command union is closed.** Rules to physics: coil pulse/enable/disable, plus the recover command for ball search alone. Rules to presentation: lamp, GI, flasher and show commands, nothing else.
- **Lamp state is a pure projection** recomputed from state every step; the loop emits only the diff, and no mode issues a lamp command. Roles are a closed union and steps are 0 to 3; no RGB, hex or colour name may appear anywhere in the simulation, and one presentation-side table is the sole role-to-colour mapping.
- **One clock, no wall-clock or unseeded randomness in the simulation.** Timers are authored in milliseconds in the tuning file, converted to ticks once at load (`shotWindowTicks()` is the one sanctioned reader for the `…Ms` window tunables), and pace presentation by emitting step events presentation animates to — presentation never reports completion. All rules randomness draws from the seeded PRNG in game state, so the Skill-shot lane and the Match number replay identically.
- **Modes have unique numeric priorities** — base 100, skill shot 200 — and speak the four-phase start and stop convention. Epic 2 runs that minimal stack only.
- **Rules tests run headless in Node with no physics or rendering loaded**, driven by the `SwitchName`-typed switch-script DSL at `test/util/switch-script.ts` (`close('s_loop_l_in').at(100).open().at(120)…`). Every device and shot event needs at least one scripted test. **The headless claim is now pinned by a transitive-closure import scan over resolved repo-relative paths, not by a comment** — its first two attempts were themselves vacuous (one scanned 2 of 76 modules; one matched raw specifiers so `../physics/machine` never matched `sim/physics`). Integration tests that reach `FrameOutput` through the loop's `advance` are a separate obligation — Story 2.3 found both of its modules had **none at all**.
- **Layering is law and is linted.** Device-name string literals outside the table file and the test tree are errors, so every new switch, coil, lamp and device name enters through the registry. `tools/boundary-lint.mjs` gained check **(g)** `rules-no-switch-event-outside-devices`, which is **textual, not a dependency-cruiser module rule** — with `parser: 'swc'` and `tsPreCompilationDeps: false` (pinned off by AD-16, which forbids a compiler-API lint), a type-only edge is indistinguishable from a value import, so a module rule would fire on two innocent files *and still miss a real leak*. It catches **five** binding forms, including a namespace-import alias with property access and an inline `import()` type expression. Three complementary provenance gates exist and none may be retired in favour of another: a per-file **presence** check, a **structural** provenance test (upstream copyright block intact, provenance sets disjoint, the solver-constant pin, the port-body freeze), and the **import** linter. Story 2.0 is the structural gate's documented owner.
- **Blender owns placement, the registry owns wiring, the export script enforces the contract.** Node prefixes are load-bearing. The export validates the source against a dump of the registry and writes both the render asset and a collision file in table-frame millimetres; the simulation never parses the render asset, and both loaders fail fast on a missing node or unknown property.
- **Tunables carry a source and a confidence.** Material parameters are named entries with scatter at zero. Scoring values stay adjustable through Epic 2 and freeze only after Epic 3's first full playtest.

## UX & Interaction Patterns

- **One fixed authored camera, no camera controls.** Both flippers, the Dragon, both Loops, the Ramp and the DRAGON bank must all be legible from it. The backbox strip that carries the Backglass is **not** yet part of that framing obligation — no backglass or backbox geometry exists anywhere (`cabinet_root` is authored childless), so Story 2.6 authors the quad and owns any camera consequence.
- **The Backglass is a low-resolution dot-matrix display** — a visible dot grid, no smoothing — showing every player's score with the current player highlighted, the ball number, and the highest-priority mode's name and whichever fields it publishes, converted to display units in presentation.
- **Presentation never joins a tick-*t* event to a later snapshot.** An end-of-ball screen names the player from the event payload, never from the snapshot that has already advanced.
- **The colour grammar is fixed and never varies**: white for a lit or qualifying shot, orange for DRAGON letters and the Lock, red for Hurry-up, green for Quick multiball, blue for Joust, purple for extra ball and special. Progression within a colour is a brightness and blink ladder expressed as the step value, with cadence timed by presentation.
- **Flipper buttons move the lit insert** one position per press across the Top lanes and across the inlane/outlane set, wrapping.
- **Attract in this epic is minimal**: the Backglass cycles the last game's scores with a start prompt and shows the flipper, plunge and Start keys once from the view configuration. The camera walk-up belongs to Epic 4.
