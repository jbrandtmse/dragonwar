## Intent

**Problem:** DragonWar has no modes. `GameState.modes[]` is declared, `ActiveModeState` and `ModeView` are declared, the Backglass already renders the highest-priority mode's name, `lane_entered { lane }` and `lane_change_pressed { side }` are already emitted by the devices layer, and `GameState.rng` is already seeded from `GameStart` — and **not one of those is connected to anything**. `src/sim/rules/modes/` does not exist, nothing has ever pushed an entry into `modes[]`, no code anywhere reads or advances `rng`, and there is no scoring value in `tuning.ts`. The plunge is therefore a bare ball launch: no Skill shot, no lit lane, no lane change, no award.

**Approach:** Introduce the **minimal mode stack** AD-8 names for Epic 2 — base (priority 100) and skill shot (priority 200) — in `src/sim/rules/modes/`, driven from the existing device and lifecycle events, plus the project's first seeded PRNG (`src/sim/rules/rng.ts`, AD-3) and its first scoring tunable. The base mode owns `players[i].lanes`; the skill-shot mode draws the lit Top lane once on `ball_starting` and resolves on the first playfield closure after the plunge. The devices layer gains one new event, `playfield_switch_closed { switch }`, because "the first playfield closure" is not decidable today (slingshots, pops, the drain and a bare ramp switch produce no device event at all), and AD-19 forbids a mode from reading a raw `SwitchEvent`. Presentation gains one mode-name → display-label entry so the skill shot reads `ARM YOURSELF`.

## Boundaries & Constraints

**Always:**

- **AD-3 — all rules randomness draws from `GameState.rng`.** The PRNG is a pure function of `RngState` (a `number`), authored in `src/sim/rules/rng.ts` and returning `{ rng, value }`. `Math.random` is lint-banned inside `sim/` (`tools/boundary-lint.mjs:119`, rule `sim-no-banned-global`); `Math.imul` is **not** banned, so a mulberry32/xorshift-class generator compiles clean. No wall clock, no `Date`, no `globalThis`.
- **AD-19 — modes never see a raw `SwitchEvent`.** `tools/boundary-lint.mjs`'s `rules-no-switch-event-outside-devices` fails on the *token* `SwitchEvent` anywhere under `src/sim/rules/` outside `devices/` — including in a type-only import or a binding list. The new `playfield_switch_closed` event is emitted by `sim/rules/devices/`, and the modes consume it.
- **AD-1 / AD-16 — no device-name literals.** `DEVICE_NAME_PATTERN = /^(?:s|c|l|f|gi|bd|shot|show)_[a-z0-9_]+$/` (`tools/boundary-lint.mjs:97`) is an error outside `src/sim/table/dragonwar.ts`. Every lane, switch and set is derived from `TABLE` (`Object.entries(TABLE.laneWiring)`, `Object.keys(TABLE.switches)`, `TABLE.ballDevices[*].slots`) — never a second hand-typed list. Lane ids (`top_1`) do not match the pattern but the DW-149 derive-from-`TABLE` convention still applies.
- **AD-15 — every new tunable carries `source` and `confidence`.** An authored figure ships `confidence: 'unverified'` with the authoring stated in `source`, in the file's established register (`source` begins with the literal token `authored: `, names the artifact that states the *mechanism*, and explicitly denies a figure). **A fabricated citation is worse than an honest "no artifact states this figure."** Non-ASCII is written as an escape sequence, never a literal byte (Rule 14) — match `tuning.ts`'s existing `§` / `…` usage. Tab indentation, and the `entry(` layout must stay parseable by `src/host/dev/tuning-source.ts` (value inline right after `entry(` followed by a comma, **or** `entry(` ending the line with the value alone on the next line).
- **AD-15 — a tunable's `source` and `confidence` are part of the hashed contract.** `resolveTuning()`'s whole serialised output is compared against `header.gameStart.tuning` in all five goldens; `tableHash()` hashes the whole frozen `TABLE`. Both change here, so this story carries **one deliberate header-only refresh of all five goldens** (see Design Notes for the exact budget and procedure).
- **AD-7 — ownership scopes.** `lanes` is player-scoped and owned by the base mode; the skill-shot mode writes the lit Top lane **once** on `ball_starting` from `rng` **and never again**. Mode-local fields stay under `modes[i]` and reach presentation only as a `ModeView`. `GameState` stays plain, JSON-serialisable data with no closures, mutated only inside `rules.step`.
- **Factory + closure, never module-level state.** `createModeStack(...)` returns `{ step }`, mirroring `createBallController` / `createDevicesLayer` (Story 2.3's module-level `occupied` leak is why).
- **Rule 19 — every AC's pinning test has a demonstrated mutation.** Named up front in `## Verification`; each must be applied, observed red, reverted, and the tree confirmed byte-identical (`git status --short` and `git diff --stat` unchanged).
- GPL-3.0 licence header on every new file (`pnpm check:headers`).

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|---------------------------|----------------|
| Ball starts, stack arms | `ball_starting` for player *p* | Base mode (100) starts **first** and resets `players[p].lanes.lit` to all-false for both groups; skill shot (200) starts **second**, draws one Top lane from `state.rng` (advancing it), sets that lane's `lit` flag true, and records the draw. `modes[]` = `[base, skill_shot]` | No error expected |
| Backglass shows the arm | Single player, `modes[]` as above, `screen: 'score'` | The rendered `DmdFrame` rows are `[<score>, 'BALL 1', 'ARM YOURSELF']` and the rasterised buffer lights dots | No error expected |
| Skill shot made | First `playfield_switch_closed` after `ball_launched` is the lit Top lane's switch | `players[p].score += TUNING.skillShotAward.value`; one DRAGON letter appended; skill shot removed from `modes[]`; base mode remains | No error expected |
| Skill shot missed | First `playfield_switch_closed` is any other playfield switch (`s_sling_l`, `s_pop_2`, `s_drain`, an **unlit** Top lane, …) | Skill shot removed from `modes[]`; score and letters unchanged | No error expected |
| Lane change, Top group | `lane_change_pressed { side: 'right' }`, `lit = { top_2: true }` | Lit pattern rotates one position by `order` within the group, wrapping: `lit = { top_3: true }`. A further `right` wraps to `top_1` | No error expected |
| Lane change, in/out group | `lane_change_pressed { side: 'left' }`, `lit = { outlane_l: true }` | Wraps to the highest-`order` member of that group, `outlane_r` | No error expected |
| Lane change is a permutation | Any `lit` pattern, either side | The **count** of lit flags in each group is unchanged; both groups rotate on the same press | No error expected |
| Top set completes | Entry lights the third Top lane | `'top'` appended to `players[p].lanes.completedSets`; `lanes_completed { set: 'top', tick }` emitted on `RulesStepResult.modeEvents`; all three Top `lit` flags reset to false | No error expected |
| In/out set completes | Entry lights the fourth member of the inlane/outlane group | Same handling with `set: 'inout'` | No error expected |
| All letters already spelled | Skill shot made, `players[p].letters` already contains all six of DRAGON | Award still pays; `letters` unchanged (no seventh letter, no duplicate) | No error expected |
| No Top lane lit | Skill shot armed but the lit Top lane was cleared by a set reset | First playfield closure resolves the mode with **no** award | No error expected |
| Non-playfield closures are inert | `s_shooter_lane`, `s_trough_2`, `s_lock_1`, `s_flipper_l`, `s_start`, `s_tilt_bob`, `s_slam_tilt` close | No `playfield_switch_closed` emitted; the skill shot stays armed | No error expected |
| Attract | `phase !== 'game'` | No mode is ever pushed, `rng` is never advanced, `lanes` is never written | No error expected |
| Ball ends | Drain outside a save window | Ball controller credits `modesPlayed` with `['base','skill_shot']` (or `['base']`) and clears `modes: []` — unchanged Story 2.5 behaviour. **[AMENDED 2026-09-06, lead, intent gap 1 — Rule 5 tier-1.]** The next ball's modes arm on the tick **after** `ball_starting`, not the same tick. The original "re-arms in the same tick" wording is *factually impossible* against delivered Story 2.5 behaviour, which this spec's own Block If protects: `ball-controller.ts:254` emits `ball_will_start`, `ball_starting` and `ball_started` in **one** event batch, and on a drain that rotates players that batch lands in the **same tick as `ball_ended`** — so `test/rules-lifecycle.test.ts`'s Story 2.5 pin, which asserts `modes` is strictly `[]` at the end of that tick, cannot hold if arming is same-tick. Arming is therefore deferred one tick **uniformly**, mirroring the codebase's existing N→N+1 idiom (`sim/rules/index.ts` already queues `ball_will_start` for the next tick's devices layer, "mirroring AD-4's own 'commands issued at tick N are consumed at N+1' shape"). Uniform, not conditional: a rule that defers only on a detected same-tick collision is more code, more branches and a timing rule that changes with context, for a difference of one tick that no player can perceive. The story's own acceptance criterion pins arming to `ball_starting` **firing**, not to a tick index, so intent is preserved | No error expected |

**Scope boundary against Story 3.1 — read this before adding lifecycle events.** `epics.md:1648` charters Story 3.1 "The mode stack", whose AC 1 opens "*Given the minimal stack from Story 2.7, when it is **generalised** in `src/sim/rules/modes/`*". **Why the skill shot resolves on one event stream.** AC 2's Given ("*enters the lit Top lane before any other playfield switch closes*") and its Then ("*when the first closure is any non-Top-lane playfield switch, the mode stops with no award*") are the same rule stated from both sides, and PRD FR-18 settles it: "*the Skill shot is only available until the first other switch closes.*" So: **the first playfield closure of the ball resolves the mode — award if it is the lit Top lane's switch, no award otherwise, stop either way.** Resolving on the single `playfield_switch_closed` stream (rather than racing `lane_entered` against it within one tick's event array) removes an intra-batch ordering hazard, and the two events describe the same closure, so AC 2's `lane_entered` wording remains literally true. Note the consequence for an **unlit** Top lane: it stops the mode with no award, because it is a closure and it is not the lit lane. A design that treated an unlit Top lane as inert would let a later entry into the lit lane still award, which the Given forbids.

**Why the lit flags are a rotating pattern, not a single cursor.** AD-7 says `lanes` holds "lit **flags**" (plural) and "completed sets", and those two fields are all `PlayerLaneState` has. AC 5 needs "all three Top lanes have been entered this ball" to be decidable, and the only place that can live is the lit flags. So: entry lights a lane and it stays lit; lane change rotates the whole pattern within each set (a permutation, so the count is invariant); all-lit completes, records and resets. At `ball_starting` exactly one Top lane is lit — the skill-shot draw — which is why AC 3's "*the lit insert … moves one position*" reads as a singular at the moment the player is actually using lane change, before the plunge. This also makes the user story's promise real ("*the flipper buttons to move the lit lanes, so that I can steer which lane is lit*"): the player can rotate the lit lane before plunging, and the skill shot pays on whichever lane is lit at the moment of entry, because it reads `lanes.lit` rather than caching its own draw. Story 2.8's AC 5 corroborates the split — it distinguishes "the lit lanes" (white, step 1) from "the skill-shot lane" (blinks at step 2), which is a *presentation* distinction over the same state plus the presence of `skill_shot` in `modes[]`.
