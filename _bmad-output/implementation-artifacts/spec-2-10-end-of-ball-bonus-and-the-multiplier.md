## Intent

**Problem:** Every ball's letters and Loops accumulate nothing. `players[i].bonus` exists (`PlayerBonusState { byCategory, multiplier }`), is seeded once at `ball-controller.ts:208` and read once at `ball-controller.ts:612-613`, and **nothing between those two lines ever writes it**; `ball_ended` ships `total: 0` hardcoded; there is no `bonus_count_step` event, no `bonusCountMs`, and no bonus scoring value anywhere in the tree. Separately, `RulesStepResult.modeEvents` — the channel carrying `lanes_completed { set: 'top' }`, the event this story's multiplier advances on — has **no production consumer at all** (`DW-208`): its only reader in the whole repository is `test/util/switch-script.ts:247`. So the ball has a payoff field with no producer, and the multiplier has a trigger the shipped product cannot see.

**Approach:** Introduce `src/sim/rules/bonus.ts` as the single owner of the bonus vocabulary and arithmetic — a closed `BonusCategory` union (`letters | loops | strikes`), the fixed multiplier ladder `1 → 2 → 3 → 5`, and two pure folds. `src/sim/rules/index.ts` calls one fold over `deviceResult.events` immediately **before** the ball controller (so a category credited on the drain tick is in that ball's own payload) and the other over `modeStackResult.events` immediately **after** the mode stack — the second being `DW-208`'s production consumer, at the same composition point where `applyDeviceEvents` and `deriveDeviceSlots` already fold events into state. The ball controller keeps what only it can own: the per-ball reset inside `startBall()`, and — from the pre-rotation `endingPlayer` snapshot it already captures at line 575 — the total, the first `score` write it has ever made, the real `ball_ended` payload, and a closure-held count-up schedule that emits `bonus_count_step` events paced by a new `bonusCountMs`. The Backglass's existing `ball_ended` screen animates to that stream.

## Boundaries & Constraints

**Always:**
- Every bonus write goes through `src/sim/rules/bonus.ts`; the categories, the ladder and the per-category values have exactly one definition each.
- `players[i].bonus` is player-scoped and mutates only inside `rules.step()` (AD-7). `src/sim/loop/**` writes no `GameState` field — gated at source by `test/ad7-device-slots.test.ts:432-490`, which permits exactly two writes to the loop's `state` binding.
- Every new tunable is a `TuningEntry` with `source` and `confidence: 'unverified'` (AD-15). `bonusCountMs` is a **top-level** `…Ms` scalar (`assertNoNestedMsKeys()`, `tuning.ts:739-757`); the three scoring values carry **no** unit suffix, following `skillShotAward` (`tuning.ts:643`).
- `bonus_count_step` is payload-complete (AD-9): presentation renders each step from the event alone and never joins it to a later snapshot. Rules never format text.
- Device names never appear as string literals outside `src/sim/table/dragonwar.ts` (AD-16; `DEVICE_NAME_PATTERN` at `tools/boundary-lint.mjs:97` matches `shot_left_loop` and `shot_left_loop_made`). The shot→category mapping is declared data in `TABLE`, derived at the consumer.
- Every drain-driving test runs at a **non-saving** tuning (`NO_BALL_SAVE_TUNING`) or seeds the device disarmed. A live save returns from `ball-controller.ts:593` before the entire end-of-ball path.
- Any harness built to re-record the goldens lives in the scratchpad, never under `test/` (a `test/**/*.test.ts` file silently joins `pnpm test`).

**Block If:**
- Any golden's `expectedHash`, `expectedGameStateHash`, `expectedCheckpointHashes`, `checkpointTicks`, `transitions`, `coilPrologue`, `durationTicks` or `header.assetHash` moves. That is a trajectory or state-hash re-record, which needs the author's explicit grant and is **out of this story's budget** — HALT and report; never re-record around it and never switch a check off.
- The implementation would require `src/sim/loop/**` to write any `GameState` field (see `## Design Notes`, "Why DW-208's fix is rules-side").
- A `GameState` field would have to be added under `machine` (machine-scoped state is present in all five goldens' `attract` snapshots, so it moves `expectedGameStateHash` — a state-hash re-record).
- The suite shows a red `check:ad7`, `check:corridor` or `check:reachability`. Every gate is expected green; a red one is a regression, not the status quo.

**Never:**
- Never invent a producer for the `strikes` category. Epic 2 has no War mode and no Strike event; `strikes` stays 0 all epic (see `## Design Notes`).
- Never advance the multiplier on `lanes_completed { set: 'inout' }`, and never advance it past the ladder's last rung.
- Never add a `GameState` field for the count-up schedule, and never add a lamp, GI, flasher or show. No new `CoilCommand`. No Backglass screen beyond the existing `ball_ended` one.
- Never compute a test's expected value from `bonusCountMs`, `bonusLetterValue`, `bonusLoopValue` or `bonusStrikeValue` by re-importing it (epic vacuity #43). Never derive a non-vacuity guard's expected count from the helper it is guarding (#44).
- Never write `players[i].score` outside the ball controller's drain branch in this story. Never decide `DW-204`, `DW-212`, `DW-226` or `DW-232`.
- Never touch tilt detection — `machine.tilt.tilted` stays unset until Story 2.11. This story ships only the read-side forfeit.

## Design Notes

**Governing architecture decisions (Rule 6).** **AD-19** is the primary: it names *"modes, **scoring** and the ball controller"* as the consumers of device and shot events, and `src/sim/rules/bonus.ts` is the scoring peer that AD-19 has always described and the tree has never had. **AD-7** fixes the scopes — bonus by category and multiplier are player-scoped, `GameState` mutates only inside `rules.step()` — and is the decisive constraint on `DW-208` (below). **AD-18** puts the drain, the ball end and therefore the payment under one arbiter, the ball controller. **AD-9** governs `bonus_count_step`'s payload-completeness, and its own Rule already names `ball_ended { player, bonusByCategory, multiplier, total, tilted }` as the worked example of a payload-complete event. **AD-3** governs the pacing: *"every display-paced sequence (**bonus count-down**, Match reveal, …) is authored in ms in `tuning.ts`, converted to ticks once at load, and drives presentation by emitting step events; presentation animates to them and never reports completion"* — this story is the first implementation of that clause. **AD-15** governs the four tunables and the golden budget. **AD-11** puts the shot→category mapping in `TABLE`; **AD-16** is why it cannot live anywhere else. **AD-6** supplies the drain semantics the payment hangs off. **No AC contradicts any AD Rule.**

**Consumes:** Story 2.4 (`bank_target_down`, `shot_*_made`, `device_ball_entered`, the devices layer's whole event vocabulary) · Story 2.5 (the ball controller, `startBall()`, `ball_ended`, `ballsInPlay`, player rotation and game over) · Story 2.6 (`advanceBackglass()` / `renderFrame()` / `rasterise()` and the `ball_ended` screen) · Story 2.7 (the base mode, `lanes_completed`, `RulesStepResult.modeEvents`) · Story 2.9 (the ball-save early return, and the `NO_BALL_SAVE_TUNING` override idiom every drain test here depends on) · Story 2.3 (the DRAGON drop bank that produces `bank_target_down`) · AD-15's tuning resolver (`shotWindowTicks()`).

**Consumed-by:** **Story 2.11 (Tilt)** — this story ships the read-side forfeit (`total: 0` when `machine.tilt.tilted`), which nothing sets true until 2.11; 2.11 makes AC 5 reachable in real play. **Story 2.13 (Game over, Match, Attract)** — the final scores it shows include the bonus this story pays, and it owns the Backglass line budget the BONUS row shares. **Story 3.7 / the War (Epic 3)** — the first producer of the `strikes` category. **Story 3.11** — the playtest freeze that turns the four `unverified` tunables into `playtested`.

**Integration ACs (Rule 1).** This story introduces two shared surfaces and both carry an integration criterion against a real consumer, not against internal state. `bonus_count_step` → **AC 8**, asserted on the Backglass's rendered DMD rows through the exact fold `src/host/boot.ts:291-292` performs, with the `events: []` re-fold as its control. `src/sim/rules/bonus.ts` → **AC 7**, asserted on the `GameState` that `rules.step()` returns to a real caller, with the `sim/loop` source gate proving no other layer wrote it. `bonusTotal()`'s third category has no producer this epic, which is stated below rather than faked.

**Why `DW-208`'s fix is rules-side, and not the loop channel its note names.** The entry's root cause — *"`RulesStepResult.modeEvents` has no production consumer"* — is exactly what task 6 closes. Its note goes on to say *"must add the `sim/loop` channel"*, and that half is not implementable as written: `AD-7`'s Rule is *"mutated only inside `rules.step`"*, enforced at source by `test/ad7-device-slots.test.ts:432-490`, which asserts that the **only** two writes to `sim/loop`'s `state` binding in **every** `.ts` under `src/sim/loop/` are the boot construction and `state = rulesResult.state;`. The multiplier is `GameState`, so the loop cannot advance it; a loop that merely forwarded `modeEvents` into `FrameOutput` would satisfy neither AC 2 nor AC 7 and would build a fifth `FrameOutput` channel with no reader — the precise vacuity Story 2.7's own `Never` section cited when it declined to emit `lane_lit`. The tree already says so twice, in `src/sim/rules/index.ts:131-140` (*"its only consumer, Story 2.10's bonus multiplier, is rules-side"*) and `src/sim/rules/modes/events.ts:7`. So `DW-208` is **addressed, not declined** — by AC 7 and task 6 — and its note's suggested mechanism is recorded here as measured against AD-7 and replaced, so the adjudication gate reads a decision rather than a surprise.

**The score-ownership decision, made deliberately.** `players[i].score` has exactly one increment site in the whole codebase today, `src/sim/rules/modes/skill-shot.ts:130`; the ball controller has never written it. This story makes it the second writer, and the reasoning is that no other module *can* be correct here. The payment needs three facts that exist only inside `ballController.step()`'s drain branch: that the ball ended at all (the branch is entered at `:566-574`, and the ball-save early return at `:593` means "a parking entry took `ballsInPlay` to 0" is **not** sufficient), which player it ended for **before** rotation (`endingPlayer`, captured at `:575`, and `startBall()` moves `currentPlayer` at `:629`), and that player's bonus **before** teardown (`:596`). Handing those to a scoring module would create a second owner of "the ball has ended", which is precisely the seam AD-18 exists to keep single. The precedent in the same file is explicit: the letters accumulator at `:451-467` is commented *"Not a mode, not scoring -- raw per-player state the ball controller already owns the write scope for"*. Accumulation stays in `bonus.ts`; **payment** — the one act that needs the pre-rotation, pre-teardown snapshot — is the ball controller's, and it happens in the same `players` map as teardown so the two cannot diverge. Governed by **AD-18** (single arbiter) and **AD-7** (player-scoped, inside `rules.step`).

**Why the two folds sit either side of the ball controller.** `creditBonusFromDeviceEvents` runs at `index.ts:236`, before the controller, so a `bank_target_down` on the drain tick lands in that ball's own payload — the same tick position at which the letters accumulator already reads that event, so the two can never disagree. `advanceBonusMultiplier` must run after `modeStack.step()` at `:246`, because `lanes_completed` does not exist before it and the stack's position after the controller is load-bearing (`index.ts:240-245`). The residual: a `lanes_completed { set: 'top' }` on the **exact** drain tick advances the multiplier after that ball's `ball_ended` was built. It is unreachable in Epic 2 — a Top-lane rollover and a trough entry are two switches one ball cannot close on one tick, and Epic 2 has no multiball — and even when Epic 3 makes it reachable, "a multiplier earned in the same millisecond the ball drained does not pay on that ball" is a defensible answer, not a defect. Recorded so a later reviewer reads a decision rather than discovering an accident.

**Why the count-up schedule is closure state.** `GameState` is hashed (AD-15) and `machine` is present in all five goldens' attract snapshots, so a machine-scoped schedule field would move `expectedGameStateHash` on every golden — a state-hash re-record, which is out of budget and a Block-If. A player-scoped field would be hash-free (the goldens' `players[]` is empty) but is wrong scope: the schedule is a display pacer, not a fact about the player. So it follows the established closure pattern (`pendingLockLaneClosure`, `awaitingSaveLaunch`, `awaitingSaveRelaunch`). The epic's rule for such a latch is two obligations — a reset at `ball_will_start` and a bounded lifetime — and this one satisfies both **by construction rather than by a reset call**, which is the part worth stating: it holds at most `steps` entries, each is emitted once at its own tick and dropped, and arming replaces any previous schedule wholesale. A `ball_will_start` reset would in fact be *wrong* here, because `startBall()` runs on the same tick as `ball_ended` and would wipe the schedule before its first step — which is why task 7(e) arms it **after** the game-over/rotation block.

**The `strikes` category has no producer this epic, and that is not a gap.** PRD FR-20 names three categories (letters, Loops, Strikes) and this story's own AC 1 names event sources for only two. A Strike is the War mode's, and the War is Epic 3: grep confirms the only `strike` in the tree is `strikesRemaining` (a `ModeView` display field no mode sets) and physics' drop-target `DropTargetStrike` collision concept, neither of which is a bonus category. So `strikes` ships as a declared category, seeded 0, with an authored value, and **stays 0 all epic**. No test may fabricate a producer for it. What the tests *do* prove honestly is that the arithmetic covers it: a seeded `initialState` with a non-zero `strikes` count contributes `count × bonusStrikeValue × multiplier` to the total, which pins the `Σ` as exhaustive without inventing an event.

**Anti-vacuity plan for four new tunables (epic vacuity #43, and Story 2.9's two repeats).** `bonusLetterValue`/`bonusLoopValue`/`bonusStrikeValue` could each be set to 0, and `bonusCountMs` to 1, and a suite whose every expectation re-imported them would stay green — which is exactly how `ballSaveGraceMs` and `ballSaveHurryUpMs` each shipped settable to 1 with the whole suite green, twice, because every behavioural assertion ran under an override tuning so the production value was never on the path. So: **AC 3's `total: 60000` is authored as a literal at the assertion**, arithmetically consistent with the shipped values but not read back from them, and **AC 4's three step offsets (400 / 800 / 1200) are authored at the probe**. The one override these two ACs use is `NO_BALL_SAVE_TUNING`, and it is what makes them production probes rather than override probes: it replaces `ballSaveMs` and `ballSaveGraceMs` and **nothing else**, so `bonusCountMs` and all three scoring values are on the path at their shipped values while the ball-save early return at `ball-controller.ts:593` is kept off it. No test in this story may override any of the four new tunables. Any non-vacuity guard added to a loop in this story must derive its expected count from an **independent** source — `BONUS_CATEGORIES.length`, or the authored fixture — never from a second call of the helper the loop consults (vacuity #44). And because a mutation is a property of a **tree**, not of a test (#48), every mutation below must be re-walked at the final tree if any line it targets was edited after it was first observed.
