Architecture walkthrough

A pinball machine, built as one

DragonWar is arranged the way a real machine is wired. Physics is the cabinet. Rules is the game CPU. Presentation is the lamp, coil and display drivers. One fixed-step clock runs through all of it, and nothing crosses a seam except the closed set of types this page walks through.

AD-1

The machine, virtualised

Every serious pinball simulator that works was built around the machine's own anatomy, not a generic game-engine stack. DragonWar takes that literally. The Rules layer is a pure function of switches — it never learns a ball's position or speed. The Physics core is a cabinet behind a virtual I/O board: switch closures come out, coil pulses go in. Presentation is a set of drivers that turn semantic commands into light, sound and motion. The Host wires them together and owns no game logic.

The one-table guard. The registry and loader are exactly the seed of a generic table runtime, and the brief names that erosion as the project's biggest risk. So: sim/table/dragonwar.ts is imported directly everywhere; there is no Table interface, no table-loading API, no plugin registration. AD-1
Discuss

Is the "no Table interface" line too strict for a future authoring path, or exactly the fence that keeps v1 a game? The layer separation preserves the option at no cost; the fence is about not paying for it early.

AD-3 · AD-4

One clock

There is exactly one time inside sim/: the tick. TICK_HZ is one constant, taken from the ported core's PHYSICS_STEPTIME — 1000 µs, so 1 kHz — and every timer in the game (ball save, grace, hurry-up, mode select, tilt settle) is authored in milliseconds and converted once at load. Wall-clock exists only in the host accumulator. If the 1 kHz spike fails and the sim drops to 480 Hz, one constant changes and the golden replays are re-recorded; nothing else moves.

Rules step after every physics step, even when there are no events — that is what lets timers count ticks. Commands issued at tick t take effect at t+1. The accumulator carries its fractional remainder; only time beyond 200 ms of debt is discarded. AD-4

AD-6 · AD-18

The Lock lane

The lane between the Dragon's legs does three jobs — lock a ball, start a mode, or count a Strike — and the founding moment of the game fires from it. Two independently built epics could each legally decide what an entry means and each pulse the Mouth. The spine closes that with a single arbiter.

Discuss

The order-free War start (spell DRAGON and lock two, in either order) means the sixth drop target can be the event that opens the mouth. The arbiter is where that moment lives — worth walking as a story before writing the epic.

AD-7 · AD-8

Who owns what

GameState is one plain JSON tree, mutated only inside rules.step, hashable and replayable. Every fact has exactly one scope. Hot seat makes this matter on day one: player 1 drains with two balls in the Lock, and player 2's credits must still read zero while the physical device still holds two balls.

Lamps are a projection, not state. lampsOf(state) is recomputed every step from the active modes by priority; the loop emits the diff. No mode ever "turns a lamp off" — it simply stops being active. AD-9
AD-10 · AD-11

Blender to playfield

Geometry has one owner — the Blender file — and devices have one owner — TABLE. The export script is what keeps them honest: it validates every node name and custom property against a dump of TABLE before writing anything, and it writes two outputs so the physics loader never needs Babylon.

Frames and units

Four coordinate systems meet here — Blender, glTF, VP units inside the port, Babylon — and the classic failure is a ball rendered at the mirror of its collision position. The spine fixes one canonical table frame (millimetres, right-handed, origin at the player's bottom-left, Z toward the glass) and sanctions exactly three conversions in one file: glbToTable(), toPhysics(), toScene(). The Babylon scene is created right-handed so the glTF loader adds no hidden flip. Pitch is never modelled in geometry: physics applies it as the gravity vector, presentation rotates playfield_root about pivot_pitch while cabinet_root stays level.

Reference dimensions are asserted, not hoped for. TABLE.reference carries the standard-body playfield (514.4 × 1066.8 mm), the ball (26.99 mm), the pitch (6.5°) and the flipper bat; the loader checks the exported bounds against them. The one browser pinball the research found was criticised first for a ball the wrong size. AD-10
AD-9 · AD-12

Light

Insert colour is how a player reads the table without instructions, so the colour grammar is held in exactly one place — presentation/lighting/grammar.ts — and rules never see a colour. They emit a role and a step (off, lit, emphasised, urgent); the grammar turns that into RGB, intensity and blink cadence. The Jackpot ladder, ball-save hurry-up and the Joust's Charge are all steps.

The lighting bet

Four channels — GI, inserts, flashers, architectural — sit behind one LampDriver. The asset contract is fixed now: every static mesh carries standard lightmap UVs and a named light group from the first model, and inserts are real geometry (a lens and a cup below the surface) lit from beneath, never decals. The per-group additive bake — the technique the dominant virtual-pinball platform ships — arrives later, behind the same driver, because it earns its place for indirect bounce and contact-soft shadows, not for light count.

On light count the research's caveat turned out stale: Babylon's clustered forward lighting runs on WebGL2 (verified 2026-08-26, about 23 lights per batch), so the WebGL2 floor has a real dynamic path and is never the degraded one. ?renderer=webgl2 forces it, and the feel test runs on both paths.

Discuss

Spike 2 — the lightmap scaling envelope — has no published numbers anywhere. The light-group partition in TABLE stays provisional until it runs. When is the right moment: before the first real playfield model, or after the geometry settles?

Deferred

Left open, on purpose

A spine stays lean by naming what it will not decide. These are pushed down with the reason they can wait.

  • Web Worker — host-only change later; postMessage snapshots only.
  • Bake pipeline — spike 2 feeds the light-group partition.
  • WebGPU-only quality — never a feature; after the floor is equal in feel.
  • Playfield geometry — epic 2's first problem, in Blender, under Lawlor's miss test.
  • Mode-start device — a separate scoop is a TABLE change, not an architecture change.
  • Hop control — one tunable; never scatter or randomness.
  • Flipper calibration, scoring values — tunables, frozen after playtest.
  • Roll synthesis, DMD technique, asset split — presentation-internal.
  • Tauri, presets, credits, gamepad, wizard mode — out of v1; nothing blocks them.
  • Gates carried — spike 1 (1 kHz over 6 bodies) and spike 3 (measured load) gate browser-first; renderer re-check due 2026-09-26; the Reference machine is unnamed.
