### Q2 — vpx_lightmapper real scaling numbers

**Headline: the project publishes NO frame-cost, texture-memory, or light-group-count budget anywhere. The `docs/` folder contains only a "Blank Table" asset and two PNGs; the GitHub wiki is enabled but contains a single line ("Welcome to the vpx_lightmapper wiki!"); an issue search for `performance` returned one unrelated result ("Three Stacktraces") and a search for `lightmap resolution` returned zero. What follows are the addon's actual coded defaults and limits, read from source — these are the only hard numbers that exist.**

The addon exposes no docs beyond the README: repo root is `.github/, .gitignore, LICENSE, README.md, addons/, docs/`, and `docs/` contains only `Blank Table`, `Core Part Library.png`, `Property-panel.png`. Repo is GPL-3.0, 27 stars, last push 2025-12-11.
- source: https://api.github.com/repos/vbousquet/vpx_lightmapper/contents/docs and https://api.github.com/repos/vbousquet/vpx_lightmapper | publisher: GitHub API | pub_date: n/a (live) | accessed: 2026-08-26 | confidence: high | class: capability

Texture atlas ("nestmap") size is an enum of `256 / 512 / 1024 / 2048 / 4096 / 8192` square, **default 256**, described as "Size of the exported texture in which rendered/baked parts will be nested (Should be greater than render size to avoid too much splitting)". Per-object bake textures (`bake_width` / `bake_height`) default 256 with `min=2, max=8192`.
- source: https://raw.githubusercontent.com/vbousquet/vpx_lightmapper/master/addons/vpx_lightmapper/__init__.py | publisher: vbousquet (GitHub) | pub_date: unknown (file, repo last push 2025-12) | accessed: 2026-08-26 | confidence: high | class: architecture-pattern

Playfield render height (`render_height`, "Render height of the playfield used to define projective baking render size") defaults to **256** with `min=256, max=8192`; a separate `render_ratio` percentage (`default=100, min=5, max=100`) scales it, explicitly intended for fast ugly previews. Nesting `padding` between packed texture parts defaults to **2** pixels.
- source: https://raw.githubusercontent.com/vbousquet/vpx_lightmapper/master/addons/vpx_lightmapper/__init__.py | publisher: vbousquet | pub_date: unknown | accessed: 2026-08-26 | confidence: high | class: architecture-pattern

The only memory-shaped control in the addon is `max_lighting: IntProperty(name="Max Light.", description="Maximum number of lighting scenario rendered simultaneously at 4K (0 = no limit)", default = 0)` — i.e. the tool assumes 4K as the reference scale for a "lighting scenario" and lets the user throttle concurrency, but ships with no limit. This is the closest thing to a published budget and it is a throttle, not a number.
- source: https://raw.githubusercontent.com/vbousquet/vpx_lightmapper/master/addons/vpx_lightmapper/__init__.py | publisher: vbousquet | pub_date: unknown | accessed: 2026-08-26 | confidence: high | class: architecture-pattern

Grouping strategy IS specified, as a three-way `light_mode` enum per Blender collection: `solid` = "Bakemap: Bake all lights in this collection as a single lighting scenario on which others are applied"; `group` (**default**) = "Lightmap: Bake all lights in this collection as a single lighting scenario to a lightmap"; `split` = "Lightmap: Bake each light as a separate lighting scenario to a lightmap". So the unit of grouping is the Blender collection, and the author decides per-collection between one-lightmap-per-group and one-per-light. A parallel `bake_mode` enum controls geometry: `group` (Merge all objects to a single mesh, default) vs `split` (Bake each object to its own mesh).
- source: https://raw.githubusercontent.com/vbousquet/vpx_lightmapper/master/addons/vpx_lightmapper/__init__.py | publisher: vbousquet | pub_date: unknown | accessed: 2026-08-26 | confidence: high | class: architecture-pattern

Named runtime-cost optimizations the addon implements, each a flag with a stated rationale: `enable_aoi` ("Area Of Influence rendering optimization", default true) restricts a light's bake to its influence region; `remove_backface` (angle limit for backfacing geometry removal, default 0.0 = full removal) and `keep_pf_reflection_faces` (default false) drop unseen faces; `is_opaque` per collection and `use_static_rendering` ("Mark this baked part to be statically pre-rendered in VPX", default true) split static from dynamic; `depth_bias` orders layers ("Set to 0 for playfield, Negative for layer above playfield, positive for layers under playfield"). Reflection/refraction probes are per-collection strings with `reflection_strength` default 0.3, `refraction_thickness` default 10.0.
- source: https://raw.githubusercontent.com/vbousquet/vpx_lightmapper/master/addons/vpx_lightmapper/__init__.py | publisher: vbousquet | pub_date: unknown | accessed: 2026-08-26 | confidence: high | class: architecture-pattern

The README states the performance rationale for atlasing and for the opaque/non-opaque split, without numbers: "the produced texture have uniform texel density (which is good for performance and visual quality)" and "each group must be marked as 'opaque' or 'non opaque'... to allow render optimization (static opaque objects are prerendered, giving a large performance boost), and to correctly process object border shading".
- source: https://raw.githubusercontent.com/vbousquet/vpx_lightmapper/master/README.md | publisher: vbousquet | pub_date: unknown | accessed: 2026-08-26 | confidence: high | class: architecture-pattern

Insert handling has explicit defaults confirming the prior round's description: `process_inserts` (default true, "Detect inserts and converts them"), `use_pf_translucency_map` (default true, "Generate a translucency map for inserts"), `insert_size` 0.0, `insert_intensity` 25.0, versus general `light_size` 5.0 and `light_intensity` 250.0. RGB LEDs are handled by `is_rgb_led` ("RGB Led (lightmapped to white then colored in VPX for dynamic colors)") — a cheap trick worth stealing: bake white, tint at runtime.
- source: https://raw.githubusercontent.com/vbousquet/vpx_lightmapper/master/addons/vpx_lightmapper/__init__.py | publisher: vbousquet | pub_date: unknown | accessed: 2026-08-26 | confidence: high | class: architecture-pattern

### Q4 — MPF scoring and ball-lifecycle devices (the reusable ontology)

Scoring in MPF is not a scoring subsystem — it is the generic **`variable_player`** config player, which "is used to set the value of player and machine variables. This is commonly used for scoring in your machine." It can create player variables on the fly, reads defaults from `player_vars:` / `machine_vars:` sections, and is addressable from two surfaces: the `variable_player:` section in config files, and a `variables:` section inside a *show step* — so a light show can award points on a given frame.
- source: https://raw.githubusercontent.com/missionpinball/mpf-docs/main/docs/config_players/variable_player.md | publisher: Mission Pinball Framework docs | pub_date: unknown (main branch, live) | accessed: 2026-08-26 | confidence: high | class: architecture-pattern

MPF's ball tracking is a four-component model, stated verbatim: "The Ball Controller, which is a core MPF module that manages everything"; "Individual Ball Devices (troughs, locks, etc.) which track how many balls they're currently holding, request new balls, eject balls, etc."; "The Playfields device which is a special type of ball device that tracks how many balls are loose on the playfield at any given time"; "Individual Diverters which are integral in routing balls to devices that request them." Critically: "These four components are active at all times---regardless of whether or not a game is in progress. In other words, if MPF is running, it's tracking balls." **The trough is not a special type — it is just a ball_device, and the playfield is modelled as a ball_device too.**
- source: https://raw.githubusercontent.com/missionpinball/mpf-docs/main/docs/game_logic/ball_tracking.md | publisher: MPF docs | pub_date: unknown | accessed: 2026-08-26 | confidence: high | class: architecture-pattern

MPF distinguishes two kinds of ball lock by whether the ball leaves play: `multiball_locks:` — "lock balls for a multiball. Locked balls are no longer in play (i.e. deducted from ball count)"; and `ball_holds:` — "which only hold balls temporarily. This is used to play animations or stop the ball during a video mode. Those balls are technically still in play." Both operate on a ball that has entered a ball_device.
- source: https://raw.githubusercontent.com/missionpinball/mpf-docs/main/docs/game_logic/ball_locks.md | publisher: MPF docs | pub_date: unknown | accessed: 2026-08-26 | confidence: high | class: architecture-pattern

`ball_saves:` is a per-mode device with a documented config surface: `active_time`, `hurry_up_time`, `grace_period`, `enable_events`, `early_ball_save_events` (e.g. outlane switches, "count outlanes as drains to speed up handling"), `auto_launch`, and `balls_to_save` (`-1` = unlimited). "MPF uses ball saves to automatically re-serve a ball that has drained. (Essentially this means the ball drain doesn't count.)" Multiple ball_saves can be configured in different modes doing different things.
- source: https://raw.githubusercontent.com/missionpinball/mpf-docs/main/docs/game_logic/ball_saves/index.md | publisher: MPF docs | pub_date: unknown | accessed: 2026-08-26 | confidence: high | class: architecture-pattern

`multiballs:` are named devices supporting several types ("run until a single ball is left, timed multiballs, etc."), configurable multiball saves ("any balls lost in the first 15 seconds of a multiball are automatically re-launched"), and **stacking of multiple multiballs simultaneously**. Each exposes monitorable properties under the prefix `device.multiballs.(name)` — including `balls_added_live` and `balls_live_target` — readable from dynamic values and conditional events. A documented real-world gotcha: MPF waits for the launcher's `eject_timeouts` (default **10s**) to confirm an eject during multiball, because playfield-switch confirmation is unreliable with >1 ball live.
- source: https://raw.githubusercontent.com/missionpinball/mpf-docs/main/docs/game_logic/multiballs/index.md | publisher: MPF docs | pub_date: unknown | accessed: 2026-08-26 | confidence: high | class: architecture-pattern

`extra_balls:` are **named and deduplicated** — "Extra balls in MPF are 'named', and they're tracked so that (by default) each extra ball can only be awarded once... Every extra ball device can award up to x extra balls (defaults to 1)." `extra_ball_groups:` cap the total across a set. The documented idiom uses conditional events on a player variable, e.g. `award_events: player_score{value>=140000}` — the same conditional-event syntax used elsewhere, so scoring thresholds are declarative, not code.
- source: https://raw.githubusercontent.com/missionpinball/mpf-docs/main/docs/game_logic/extra_balls.md | publisher: MPF docs | pub_date: unknown | accessed: 2026-08-26 | confidence: high | class: architecture-pattern

**The event vocabulary is the highest-value artifact here.** MPF's docs carry 267 individual event reference pages. The ball/game lifecycle uses a consistent four-phase naming convention — `X_will_start` → `X_starting` → `X_started` … `X_will_end` → `X_ending` → `X_ended` — instantiated for both game and ball: `game_will_start, game_start, game_starting, game_started, game_will_end, game_ending, game_ended` and `ball_will_start, ball_starting, ball_started, ball_will_end, ball_ending, ball_ended`, plus `ball_drain`, `balls_in_play`, `ball_start_target`. Modes use the same shape: `mode_(name)_will_start, _starting, _started, _will_stop, _stopping, _stopped`.
- source: https://api.github.com/repos/missionpinball/mpf-docs/contents/docs/events | publisher: MPF docs (GitHub API listing) | pub_date: n/a (live) | accessed: 2026-08-26 | confidence: high | class: architecture-pattern

Ball-device events are namespaced `balldevice_(device)_ball_*` and cover the full eject state machine: `ball_count_changed`, `ball_enter`, `ball_entered`, `ball_eject_attempt`, `ball_ejecting_ball`, `ball_eject_success`, `ball_eject_failed`, `ball_missing`, `broken`, plus `balldevice_balls_available` and `balldevice_captured_from_(captures_from)`. Note the explicit failure states — `eject_failed`, `ball_missing`, `broken` — the design assumes physical mechanisms fail and models it in the event vocabulary.
- source: https://api.github.com/repos/missionpinball/mpf-docs/contents/docs/events | publisher: MPF docs | pub_date: n/a (live) | accessed: 2026-08-26 | confidence: high | class: architecture-pattern

Feature-device events follow `(devicetype)_(name)_(verb)`: ball_save emits `enabled, disabled, timer_start, hurry_up, grace_period, saving_ball`; multiball emits `started, ended, lost_ball, hurry_up, grace_period, shoot_again, shoot_again_ended, restarted, restart_grace_period_started`; multiball_lock emits `locked_ball, full`; ball_hold emits `held_ball, full, balls_released`; extra_ball emits `lit, awarded, award_disabled` with a parallel `extra_ball_group_*` set adding `lit_awarded` and `unlit`. Ball search is its own subsystem: `ball_search_started, _stopped, _failed, _phase_(num), ball_search_prevents_game_start`.
- source: https://api.github.com/repos/missionpinball/mpf-docs/contents/docs/events | publisher: MPF docs | pub_date: n/a (live) | accessed: 2026-08-26 | confidence: high | class: architecture-pattern

Ball-start actions are hung off `ball_started` via config players with no code — the documented pattern starts music/shows on `ball_started` and starts a ball save on eject, with a mode declaring `mode: start_events: ball_started`. MPF also ships a flowchart reference for the ball-start sequence (`docs/flowcharts/ball_start.md`) and a dedicated `docs/events/ball_lifecycle.md` overview page.
- source: https://raw.githubusercontent.com/missionpinball/mpf-docs/main/docs/game_logic/ball_start_end.md | publisher: MPF docs | pub_date: unknown | accessed: 2026-08-26 | confidence: high | class: architecture-pattern

## Leads worth chasing

- **Quantify the vpinball GPLv3+ conversion.** The LICENSE claims "the vast majority of files" are converted as of Oct 2025. A clone + count of files whose first line is `// license:GPLv3+` versus total source files would turn a vague claim into a number, and would tell you specifically whether the physics code (`src/physics/*`) — the part most worth reading — is GPL or non-commercial. This is the single highest-value follow-up and needs a git clone, not an API call.
- **`neophob/wpc-emu` deserves a full round.** Apache-2.0, in-browser, actively maintained, 34 MB repo. Questions: does it emulate the WPC CPU board only (so you still need a physics/renderer host)? What is its API surface for driving lamps/solenoids/switches from an external simulation? playfield.dev is the live demo to profile.
- **`freezy/VisualPinball.Engine` (VPE)** is GPL-3.0, unambiguous, and committed to as recently as 2026-08-23. Its C# physics port from VPX is the cleanest reading of VPX's physics model available under a known license, and Unity can target WebGL. Worth a round on its physics module and on whether its VPX file importer is separable.
- **`francisdb/vpin` and `vpxtool` (Rust)** for a .vpx asset pipeline — check their licenses and whether they compile to WASM, which would put table-file parsing in the browser.
- **Effort figures**: open VPForums topic 38761 and individual VPUniverse recreation file pages, which often carry author changelogs with dates spanning the build. A first-to-last-release date span from a single table's version history is a *sourced elapsed-time* figure even if no one states hours. Pinside homebrew build logs are the other venue.
- **MPF `logic_blocks` (accruals/counters/sequences), `bonus`, and `tilt`** are the remaining half of the game-logic ontology and are cheap to fetch from the same docs repo path.
- **MPF's `docs/events/ball_lifecycle.md` and `docs/flowcharts/ball_start.md`** were identified but not fetched — they are the authoritative state-machine diagrams.

## Looked for but could not find

- **Any published performance number for vpx_lightmapper**: no frame cost, no texture memory budget, no light-group count for a real table, no bake-time figure. The `docs/` folder is three files, the wiki is a single welcome line, and the issue tracker returns nothing on `performance` or `lightmap resolution`. The addon's coded defaults (256px render height, 256px atlas, 4K reference for the `max_lighting` throttle) are the *only* numbers that exist, and they are conservative starting values, not measured limits. **Absence of evidence is the finding: nobody has published the scaling envelope for this technique.**
- **A typical light-group count for a shipped table**: not stated anywhere. The `light_mode` enum tells you groups are per-Blender-collection and author-chosen, but no example table's group count is documented.
- **Any first-person hours or elapsed-time figure for authoring one pinball table.** The best candidate (engineersneedart Teacher's Pet) turned out to be a tutorial with zero time references. Web search returned only unattributed secondhand month-scale claims that I could not anchor to a URL. **No sourced effort figure exists in what I retrieved. Do not let a number be invented to fill this gap.**
- **A per-subdirectory license manifest for vpinball.** The LICENSE says `third-party/` contents are governed by `docs\license.txt` and by per-library files, and that individual files may carry their own licenses — I did not enumerate these. Any dependency on vpinball code needs that enumeration done file-by-file.
- **A license for `patrick-s-young/pinball-xr`** — the repo has none, which is itself the finding.
- **MPF `game_logic/multiball/` and `game_logic/ball_save/` at the URLs given in the brief** — those paths 404 and the site redirects to a versioned 404 page. The real content lives at `game_logic/multiballs/index.md` and `game_logic/ball_saves/index.md` (plural, directory-with-index), and the fastest access is raw markdown from `missionpinball/mpf-docs` on branch `main` under `docs/`, not the rendered site.
